# 冠軍目標檢討：目前沒有把功能數量轉換成可靠得分

日期：2026-10-21（Asia/Taipei）。本次只閱讀既有程式、結果與公開資料，沒有重新推論、訓練、下載模型、建置映像或增加測試。程式基準為 `8852fdf`，部署 `ee7b636`，評測 `a41c12d`，文件 `62036aa`。本文件提出的修正尚未實作。

後續使用者另行要求重測。較新的實測與資源證據見 [RETEST_2026-10-21.md](RETEST_2026-10-21.md)；下文保留重測前的檢討，不將歷史觀察冒充最新結果。新觀察包括共享 GPU 記憶體壓力，以及更多獨立作者題組失敗；不能再把 GPU 瓶頸一概當成沒有證據。

## 1. 結論與責任

目前最先要修的是**錯誤放行的備援流程、模型服務的時間與狀態管理，以及證據和問題關係的判斷**。檢索品質、評分方法與開發資料偏差也很重要。沒有控制實驗可以把失分換算成「演算法占幾成、GPU 占幾成」，因此不編造歸因百分比。

| 候選癥結 | 本次判斷 | 先做什麼 |
|---|---|---|
| 演算法 / 控制流程 | 已確認有錯誤放行、關係綁定與檢索終止條件問題 | P0 狀態機與證據資格，再修關係抽取與檢索 |
| GPU 服務工程 | 已確認大量 503 / 逾時，連鎖 busy 機制仍需時間線證實 | 修請求預算、取消、排程及短輸出 |
| GPU 算力 / VRAM | 有 12GB 與 3072-token 限制；本次沒有 OOM 或算力主因證據 | 分離 prefill/decode 與上下文缺證據，不能先換卡求解 |
| 模型能力 | 同模型 verify 有語意盲點；與缺證據、服務錯誤混在一起 | 固定正確證據做 oracle reader 診斷後才比較模型 |
| 網頁資料品質 | 明確有抓取失敗、垃圾頁、錯誤或低可信來源 | 實體錨定、品質觸發再搜尋、來源分級 |
| 訓練 / 開發資料 | 同作者 fixture 與目標分布不一致，缺高品質關係反例 | 先修標註與分割；沒有證據支持現在就微調 |
| 評分方式 | 明確有格式、數值容差與替代來源問題 | 舊分數保留，另立經裁定的指標，不冒充演算法提升 |

我先前以測試通過數、解析格式數和打包完成度替代競爭力證據，並把模型服務失敗與答不出來混在總分裡。這讓大量工作沒有對準真正損失。另有儲存規劃失當、重複驗證與比較不足；這些是我的工程決策問題。

冠軍應以同條件的端對端正確率、有效來源、拒答代價與時間限制評估。已知題 100% 只是開發里程碑；不能承諾未知題、不可存取網站和有歧義標準答案上的絕對 100%，也不能以這些限制替現有可修的錯誤開脫。

## 3. 與對手比較需要修正的解讀

### Pinpoint：目前沒有證明我們的演算法領先

[作者公開 README](https://github.com/ctmakc/pinpoint-web-agent) 報告 AMD W7900D、Qwen2.5-7B、11/15。我們保留的 `public-pinpoint-comparison-hardened.json` 為 12/15。兩者使用寬鬆答案 substring 評分，不驗證來源，硬體與網路也不同。

逐題比較：我們多通過 a03、a08、a13，對手多通過 a02、a10，a15 雙方失敗。a08 是唯一沒有起始 URL 的題；對手明載其 AMD 環境封鎖搜尋，該題因此失敗。描述性分層後，**其餘 14 題雙方都是 11/14（78.6%）**。這不是重新定義官方分數，而是指出 12 對 11 不足以證明檢索演算法領先。

值得學的是其簡化模型回合：一次回覆答案、來源段落、引文與下一步連結，最多三輪；我們把 expand、select、verify、suggest-link 拆成多次呼叫，增加固定開銷與忙碌風險。原始碼亦顯示 Pinpoint 在部分情況會以搜尋摘要作候選證據；我們不採用這一點，因為正式頁面支撐仍需另外驗證。其引文存在檢查也不能證明語意蘊含。

### WebScout：結構化直達是工具，不是通用正確性的替代品

[公開 README](https://github.com/Solar-DePIN-Hub/amd-match4-agent) 報告 CPU 規則開發集 32/32、作者保留集 7/8，並明載 AMD GPU / 模型驗證尚未完成。PyPI、npm、crates、GitHub、endoflife.date、Wikidata 直達與 typed extraction 值得保留。不能把這些規則的成功推論到所有人物、歷史事件、獎項與跨頁問題。

我們已具備許多同類直達能力。下一步是把結構化資料的主體、欄位和時間綁定做對，而不是繼續堆更多 regex。WebScout 的低 CPU 延遲也不能和我們含模型的廣域測試直接比較。

### SourceTrail：額外驗證必須證明有收益

[公開 README](https://github.com/agammann/source-trail) 的 AMD Qwen3-4B 開發題：baseline 12/16、verified 11/16，壓力開發題均 6/6。它示範版本、來源及引文的可檢查性，也清楚區分開發題與正式評測。這支持「需要量出驗證帶來的正確攔截與錯誤拒絕」，不支持「多一次模型確認一定更準」。它和 Pinpoint 都有公開 AMD 模型執行證據；我們目前在這項驗證落後。

### Kaminari / ArcOmega：學控制複雜度，不能把功能表當成成績

[Kaminari](https://github.com/kaminariouji/kaminari-web-retrieval) 為標準函式庫核心、可選模型與瀏覽器、引文存在檢查，README 不主張 benchmark 分數。[ArcOmega](https://github.com/dcain2336/amd-league-match4-webretriever) 為有頁數 / hop 限制的規則流程，TinyFish 為可選搜尋服務。它們展示較小的執行面和可選昂貴功能，但未提供足以排名的共同端對端結果。不能為模仿競品而引入未授權金鑰或假設付費服務可用。

### 研究方法：採用可驗證原則，不貼論文名稱

- [CRAG](https://arxiv.org/abs/2401.15884)：先評估檢索品質，低品質時改變檢索動作，再過濾無關材料。對應我們「有搜尋連結就不再換查詢」的問題。原論文實作包含訓練過的 evaluator；目前同模型的 Boolean verify 並非等價重現。
- [Self-RAG](https://arxiv.org/abs/2310.11511)：需要訓練出的 reflection tokens / 評估能力。對同一個通用 4B 模型再問一次 supported=true/false，不等於取得該論文的收益。
- [Adaptive-RAG](https://arxiv.org/abs/2403.14403)：按問題複雜度選擇路徑，避免簡單題過度運算、複雜題只有一次檢索。我們可採用「確定欄位直達 / 一頁抽取 / 有缺口再搜尋」的預算分配原則，但其原版包含分類器訓練，不能聲稱已復現。

上述 GitHub 與 arXiv 頁面本次經 HTTPS 直接讀取；web connector 發生授權錯誤後改用一般 HTTP 讀取。官方 LabLab 頁面本次直接 HTTP 回傳 403，因此本文件不宣稱已重新確認今日官方 brief 或榜單狀態。

## 4. 每個主要問題、證據、修正與驗收

### P0-1：模型錯誤被當成允許規則接手

**證據與原因（程式及紀錄確認）**：`agent/engine.py:149` 只有 state=abstain 才設 model_abstained；503、TimeoutError、invalid JSON 等不是 abstain。`engine.py:170` 和 `:209` 仍可進 `_finish`，只靠 score>=5.5 與有限 `verify` 放行。24 個規則輸出均出現在 selector 有錯誤狀態的案例。

**修正**：把 SELECTED、NO_EVIDENCE、TRANSPORT_FAILURE、INVALID_REPLY、BUDGET_EXHAUSTED 分開；錯誤不能轉成肯定答案。只允許已獨立證明主體與欄位綁定的 registry / API / 明確表格欄位走確定性路徑，不能用網頁關鍵詞分數當替代驗證。

**驗收**：用既有故障例的離線 trace / 已有來源，確認服務故障不會回出 false、BreadcrumbList、WebPage、uri、網站導覽標題或不相關數值；同時量出原本正確的直達題是否保留。這項先改善精確率，可能暫時增加拒答，必須報告覆蓋率而不是把拒答當成功。

### P0-2：模型服務時間契約與忙碌管理不一致

**證據（確認）**：selector 有 61 次 503；43 題任一模型路徑遇 503。`navigation.py:15` 的提示 HTTP timeout 最多 3.8 秒，服務端 `model_server.py:84` 預設生成 max_time=4 秒，另有前處理 / prefill / 傳輸開銷。`model_server.py:165` 忙碌即 503，HTTP 客戶端逾時後沒有對應的生成取消或請求 deadline 協定。

**因果邊界**：逾時後背景生成持續佔鎖、造成下一次呼叫 503，是程式支持的高風險機制；現有資料沒有 per-request busy body / GPU 時間線，不能宣稱每一次 503 都已證實是此原因。

**修正**：每次請求帶剩餘預算、request ID 和明確終態；單一有界推論排程、可檢查的取消與鎖釋放、短輸出、可用的結構化解碼。可選 expand 與導航不得搶占最後讀取 / 寫檔時間；模型繁忙時先做 CPU/I/O，不連續重試灌入相同服務。模型常駐保留，不能用每題重載掩蓋殘留工作。

**驗收**：一個取消後緊接下一題的針對性實驗，確認沒有前題殘留造成的連鎖忙碌；逐階段分開計 prefill、decode、queue、HTTP 和取消時間。只有階段量測證明受算力限制，才討論換模型 / 推論 runtime。

### P0-3：網站設定與 schema 標記被當成答案

**證據（確認）**：simpleqa-1191、2943、218 回答 false；2372 回答 BreadcrumbList；2189 回答 WebPage；3236 回答網站 marketing country Belize；2642 從手機上市日期回答歷史人物題。`parser.py:212` 起將 application/json、JSON-LD 展平成證據，`candidates.py` 對泛用 text 欄位缺乏充分排除。

**修正**：保留 structured parsing，但分開「可回答的實體事實」與「UI / 執行設定 / schema 型別 / 導覽」。JSON-LD 只沿已辨識主實體和問題欄位抽取，不全域掃每個 name/value。RDF 的 type=uri 是型別標記，不是值。meta title 不能自動回答人物、日期或產品屬性題。

**驗收**：垃圾型別輸出為零，且可回答的 JSON-LD product / API / 表格欄位沒有一起被封殺。不要僅對那幾個字串建黑名單。

### P1-1：問題解析沒有表示完整的「要問什麼」

**證據（確認）**：Date 類的 12 題被標為 text；Number 類的 12 題也為 text。family 不等於完整型別標準，這些只是一個警訊。更明確的是「When ... stud fee ... how many Euros」被標成 date；許多「On what day, month, and year」為 text。`planner.py` 依開頭、focus 和 regex 推斷，沒有目標欄位與背景子句的結構表示。

**修正**：產出主體、關係、答案型別、時間粒度、數量、比較/最早/先後限制、單位、背景條件與待證明欄位。資訊型別不是只有 text：人物、地點、機構、文件標題、外部 identifier 要分開。完整日期不能只輸出年份；資產和負債不能只回一個數字。採最小規則加必要模型解構，不能每題先花數秒做複雜 planning。

**驗收**：日期、費用、排名、識別碼、雙值與表格選列/選欄等既有失敗能得到正確目標欄位；未見同義句仍使用相同結構，而非按題號或網站硬編碼。

### P1-2：欄位附近有值，不代表值回答指定關係

**證據（確認）**：491 把獎項創立 1961 當指定人物得獎 1984；1744 把出生 1922 當母親去世 1947；3986 把首位雙性戀州長當首位公開雙性戀州級官員；4197 已有正確表格列卻回欄位 NW06 而非 Lagrange；2374 以航程 300 回答高度。

**修正**：以 subject–relation–object 及 qualifier 的證據單位驗證，明確指出主體 span、關係 span、值 span、時間 span / 表格 row+column。要求正確關係，不用全頁 title 或相鄰年份補足缺口。抽取與驗證應有「哪個條件沒有證據」的結果，而非只有 supported Boolean。

**驗收**：在正確證據旁放同主題的錯關係值，不能因更多關鍵字而選錯；同一段正確證據可換文字順序，不依賴固定模板。

### P1-3：搜尋找到任何連結就停止改善，造成主體漂移

**證據（程式確認，逐題貢獻待量測）**：`search.py` 在 found 非空時跳過後續備援；連結有找到不代表內容相關。`rewrites` 可把只含 hints 的查詢放第一，裁成前三，再只執行前兩個 query；主體條件可能弱化。engine 的 search_recovered 只給有限恢復機會。實際紀錄含不相關 GitHub、手機商品與影片頁。

**修正**：查詢保留實體錨點；用實體+關係的不同改寫並行少量搜尋；依「取得可支撐事實的頁面」而非連結數判斷成功。沒有證據就依缺失欄位改寫一次 / 開下一連結；相同實體與正確文件優先，官網首頁也不能取代目標頁。保留來源多樣性但壓低 SEO 問句重寫頁與無關商店。搜尋摘要僅用於找頁，不直接作答。

**驗收**：分別量有起始 URL、無起始 URL、起始 403/404 與需一跳的 source discovery / evidence recall。若沒有完整頁面快照，不能把模型拒答硬歸因為 parser。

### P1-4：來源可支撐錯誤資訊，不能只檢查字串存在

**證據（確認）**：2757 從另一個人物傳記網站讀到 University of Warsaw 並獲模型驗證，與既定答案 University of Gdańsk 不符。這段文字表面上明確支持回覆；同模型重問不會驗出來源本身錯誤。

**修正**：使用第一手或具出處的資料，核對主體識別與時間。高風險 / 低權威 / 互相衝突時才取得第二個獨立來源；同源轉載不算兩票。區分「本文有寫」和「問題事實已確認」。不能要求所有題都兩頁交叉核對，以免 30 秒內做不完。

**驗收**：記錄 source authority、轉載關係與反證；對存在衝突的答案能指出選擇依據。沒有能力判定真假的頁面，應保留不確定性而非標高 confidence。

### P1-5：額外驗證有誤拒答，也有同模型盲點

**證據（確認）**：563 的模型已選正確 ChemSpider ID 2908，卻在 unresolved_conflict 結束。897 / 1755 的錯誤候選被 verify 攔下，顯示驗證確實有必要；但多個語意錯誤仍被 supported 放行。不能整個移除或一律多問一次。

**修正**：衝突必須是「同實體、同欄位、同時間、同權威層級」的不同值；不同實體的 ID 不構成同欄位衝突。驗證要檢查缺失條件、針對性反例或另一證據，而非把選擇者的答案再送給自己求認同。保留字串 / 型別的硬約束，對已證明的直達欄位減少重複模型回合。

**驗收**：同一組固定證據比較無額外 verifier / 現行 verifier / 改進 verifier，報告正確攔截、錯誤放行、錯誤拒絕和增加延遲。Oracle 正確證據下仍答錯或拒答，才可明確定位 reader/verifier。

### P1-6：字串嚴格評分混入格式、範圍與語意等價問題

**證據（確認有不一致，部分正確性需裁定）**：4129 的 Arlington, Va. 對 Arlington, Virginia；3522 的 Shun-ichi 對 Shun'ichi；593 的 3rd of October 1247 對 ISO 日期。262 的 781 在 gold 明載 767–783 的可接受範圍內；1542 的 2618 kJ/mol 也不能只和含說明文字的 gold 完全比較。3755 涉及分鐘換小時；224 回覆含另一個獎項，須裁定範圍而非擅自放行。

**修正**：把 raw span、可追溯 normalized value、型別 / 單位 / 精度與 citation 分開。評分解析預先宣告的 numeric tolerance、日期格式和清楚等價別名；姓名、跨語地名不可靠全域刪字誤配。轉換應附原文值與轉換規則。正式介面輸出遵循已知契約；不能以改 evaluator 冒充 production 變強。

**驗收**：保留原始 4% / 9% 報告，修正評分另列版本與逐題理由；同時報原始 exact 與預先定義的 semantic/type-aware 結果。逐題表中 12 個 NORMALIZATION_REVIEW 候選不是已判正確，也不合成新總分。

### P1-7：答案正確但來源不在 gold，不必然是壞引用

**證據（確認）**：5 題答案完全符合但來源不符，其中 1639 為賽季路徑不同、3382 為同一大學人物頁後綴不同；另外三題使用不同網站。不能把五題一律當引用正確，也不能一律當假引用。

**修正**：並列 exact gold URL、可觀察 redirect provenance、實際引文支撐性；URL canonicalization 不能只放寬同網域。若正式評測要求某一頁，需遵守；目前尚未有官方 Match 4 evaluator 證實這項要求。外部 SimpleQA gold 網址是原始參考來源，不應自動假定是唯一有效答案網址。

**驗收**：原始 gold 不修改；替代來源逐條審核後另列 citation-supported 指標，不能偷換成官方分數。

### P2-1：3072-token 上限與截斷可能丟證據，但尚非主要歸因證據

**證據（確認）**：12GB GPU 使用 3072-token input；模型只看前 8 段，每段最多 1100 字元，超限再丟最低排名段。完整頁面主體脈絡與跨句關係可能不在選中段內；健康紀錄有 9 次剪裁。沒有本次 OOM 證據。

**修正**：以主體、關係和段落多樣性選 evidence bundle，保留表頭、前後句與識別上下文；不要只把 token 上限拉滿。先比較正確證據有無進入上下文；若 gold 已在而 reader 仍錯，才調模型 / reader。必要時在可容納配置中比較更合適的 instruct reader 或量化方案，量化支援與精度必須實測，不臆測 7B 必勝 4B。

**驗收**：source recall、parsed evidence recall、context recall、oracle reader success 分開；不得只報最終答案錯就說 GPU 不夠。

### P2-2：訓練資料與測試設計偏差

**證據（確認）**：330 個熟悉 fixture 全過，但外部集大幅下降；多個 fixture 由同一作者、相近模板與問題家族產生。修完後反覆跑已看過的 holdout，使其變成 regression。沒有對 reader 做獨立證據條件控制，也沒有系統化共同比較。

**修正**：以網站 / 問題家族 / 實體分割，不只隨機分列。既有 100 題全部視為已曝露開發資料。新 holdout 事前規則固定，不因取不到頁或題目難就刪掉；另報可取得性分層。先建立高品質問題—證據—欄位標註及易混負例，再決定是否需要訓練 retrieval evaluator / reranker。不要用大量同模板資料微調模型來背答案。

**驗收**：證據 oracle 階段能區分 retriever 與 reader；未見網站 / 主體保留；所有失敗保留。訓練僅在同證據控制顯示 prompt / schema 無法解決時才啟動，且不可用 holdout gold 訓練。

### P2-3：沒有足夠的同條件競爭定位

**證據（確認）**：只有 Pinpoint 15 題的答案評分可作粗略對照；WebScout、SourceTrail 題組不同。4% 是外部集，不能作他人的成績。對手自己的分數也不是獨立排名。

**修正**：建立去重的公開題組聯集，保留原作者 scorer，另加共同的答案 / 引用標準。共同證據離線比較用來排除網路差異，live 比較另列真實取得能力。對手程式如更換模型 / 後端，明標 adapted baseline，不稱原版原條件；既有 RTX 12GB 放不下某個 BF16 模型時不能偷偷下載 / 交換大環境。

**驗收**：逐題 paired win/loss/tie、延遲、來源、拒答和樣本數；小樣本不轉成全體百分位。冠軍目標至少要求超過可重現 baseline，尚無結果時要明確寫未驗證。

### P2-4：信心、逾時與系統觀測未反映真正風險

**證據（確認）**：confidence 只是關鍵字分數的公式；外部集 >=0.9 的六個輸出聯合評分全錯。直接 engine 有 2 題超過 30 秒；輸出契約和模型回覆錯誤則混在各種 fallback 中。

**修正**：排名分數不要包裝成機率。若沒有獨立 calibration 資料，就用可解釋證據狀態或不輸出 probability。追蹤每段時間、模型 busy 原因、原始/normalized answer、確切引用與拒答條件。單一 query 的總 deadline 要覆蓋解析、瀏覽器與收尾，保留寫檔時間。

**驗收**：預先定義的選擇風險 / coverage 與 p95、最長 CLI 時間一起報；不得用把所有題拒答來換「無錯誤輸出」，也不能單憑提高 confidence threshold 宣稱高準確率。

### P3：部署、儲存與交付仍有未完成事項

**證據（確認）**：ROCm 映像已建置與匯出，AMD 全模型核心運算未驗證；因儲存壓力取消空 daemon reload；最終來源 ZIP 未重打包。之前基底快取和 VM disk 多重儲存占用過大，已清回約 129 GiB。這些不是語意錯題的根因，但可造成最終無法提交或驗收。

**修正**：保留已完成映像與模型；只在 production 有實際變更且需要交付時重建。先估算 pull/build/export/reload 的同時峰值與現有硬連結，確保每個昂貴中介物只有必要份數。AMD 最終驗證、來源包與正式提交各自列清楚狀態。禁止覆蓋 ROCm PyTorch、禁止引入 CUDA-only production dependency。

**驗收**：最終 AMD query 真正使用 HIP，全模型延遲和 VRAM 有紀錄；官方契約來了只換 adapter。沒有正式結果就不稱已提交或冠軍。不能為補文件再建一份 40GB 映像。

## 5. 執行順序與改進收益的證明

1. **先修會製造假答案的 P0**：狀態機、只允許可信確定性欄位備援、來源事實與 UI metadata 分流、取消/忙碌管理。用現有錯誤證據與最少必要針對性驗證確認，不跑百次全面回歸。
2. **再修每次推論真正讀什麼**：關係式 query spec、同實體欄位綁定、表格 row/column、明確的證據缺口、少回合的 reader/navigation。避免以增加呼叫次數替代判斷。
3. **再修取得什麼資料**：實體錨定的 query rewrite、低品質結果觸發有界再搜尋、主體與來源可信度；分離取得失敗與讀取失敗。
4. **修評分與資料表示但保留舊分數**：原文 / 正規值、日期粒度、數值容差、單位、有效引用。不把 evaluator 改動算成 production 準確率提升。
5. **在固定證據下做最小消融**：有/無問題狀態修正、有/無新 rerank、有/無新 verify，報淨新增正確與新失敗。若 reader 在 oracle 證據下仍差，才比較可容納的模型配置 / 有依據的訓練。
6. **最後做公平競品比較和新 holdout**：一次預先定義的檢索策略評估，不在新 holdout 上迭代；完成後才依需要做最終 AMD、container、submission。

每一批開始前寫出「可觀察問題 → 預期改變 → 一個能否定假說的驗證」。如果只有新增功能、沒有改善該失敗或真實勝率，就不擴大。硬體與訓練不是免責理由，也不是預設下一步。

## 6. 100% 的具體拆解

- **可以要求 100% 的工程規則**：答案出處可追溯、不把服務錯誤當成功、不回網站設定作事實、不更動 frozen gold、不隱藏失敗、資料與模型不偷換、輸出遵守契約。
- **已知公開 15 題的目標**：15/15 且人工檢查證據；其中空白題也必須有正確拒答理由。它是熟悉開發題，不是全體實力或冠軍證明。
- **新的可取得證據 holdout 目標**：向 100% 攻，每個殘餘失敗有完整階段歸因；任何 95% 等數字只能是事前訂的工程目標，不能說是已知奪冠門檻。另列所有題的總分，不能只展示可取得子集。
- **仍有外部不可控與評測不確定性**：403/404、原文錯誤、答案歧義、正式 hidden distribution。必須量測與分層，不保證未知資料絕對 100%，也不因此停止能做的工程。

# Parse complete cutoffs and retain unresolved date requirements

The old `as of` regex accepted a prefix of the requested value. `2020.2` and
`2020-02` became `2020-12-31`; impossible `2020-99-99` remained a cutoff.
Unrecognized text such as `next summer` disappeared, allowing a registry's
current-version fast path to answer a historical question.

`agent/temporal.py` now reads a complete calendar literal and validates it with
the standard calendar/date library. Supported inputs include a year, ISO
month/date, unambiguous numeric dates and English month-name dates. Year-only
cutoffs retain the existing end-of-year convention; month-only cutoffs use
the final calendar day of that month, including leap years. This is a stated
comparison-bound policy, not a day copied from the question or answer gold.
`now`/`today` permit current lookup. Named censuses retain their separate
[observation-year behavior](CENSUS_REFERENCES_2026-10-23.md).

Impossible dates, locale-ambiguous dates, conflicting cutoffs, unsupported
formats and hour-level timestamps have explicit `temporal_issue` and
`temporal_raw` plan metadata. The complete question is also retained.
The engine returns an empty answer before creating the fetcher or calling
resolvers/models for such a plan. Direct candidate verification also rejects
it. Merely removing an unparsed cutoff and answering a current value is not
allowed. These are internal diagnostics; minimal answer/source JSON is
unchanged.

- `benchmarks/cutoffs-20261023-before-v3.json`: **10/52** assertions pass.
- `benchmarks/cutoffs-20261023-after-v3.json`: **52/52** pass.

grammar variants are not independent factual questions or accuracy estimates.
Earlier attempts are retained. In particular, the expanded range/time checks
exposed five omissions in the initial parser; the final parser handles those
without truncating a spaced time or date range into one date.

Twelve complete-engine checks use actual loopback HTTP, including a controlled
registry transport. Public PyPI URLs in that replay identify the adapter;
only the local fixture is contacted, with invented metadata. It is not a live
primary-source measurement.

The sparse release table changes from version `2.0` in November to `1.0` in
January for a February cutoff. An English March cutoff changes from `2.0` to
the literal March release `1.2`. The original dense table already happened to
answer February correctly because of lexical ranking despite its wrong year-end
plan; that case is retained, not counted as a new end-to-end answer win.
An unresolved `next summer` registry request previously returned current `9.0`;
now it has no fetch or model calls. Valid current lookup still returns `9.0`.

Three fresh CLI/isolated-worker checks additionally preserve exact minimal

## Remaining evidence issue

Relative seasonal dates and timestamp-level cutoffs are not resolved; they
abstain instead of becoming an unconstrained current lookup. Generic temporal
language is not universally parsed by this change.

The next controlled probe (`cutoffs-20261023-next-field-probe.json`) also
exposes a separate issue: a current-only registry license, with no historical
date witness, can still be selected for an otherwise valid historical cutoff
when the CPU semantic stub blindly supports it. Cutoff parsing is now retained,
but field-level historical evidence remains insufficient. That is not fixed
or counted as fixed here.

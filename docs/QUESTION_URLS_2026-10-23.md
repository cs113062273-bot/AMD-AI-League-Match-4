# 問題文字中的網址保持完整

這一步只使用 CPU、本機 HTTP 與模型關閉的 CLI／worker。沒有載入權重、使用 GPU、啟動瀏覽器或呼叫公開 API。

## 問題與修正

原本的規劃器把所有右括號當成網址終點，例如問題中的 `https://example.org/Plum_(tree)` 會變成 `https://example.org/Plum_(tree`。這會讀取錯誤來源。直接傳入獨立 `--url` 的路徑原本不受這個問題影響。

新的文字網址掃描保留內部成對括號、IPv6 的方括號及原始百分比編碼，並區分外層 Markdown／引號標記。多個網址仍保留原順序，查詢參數中的另一個網址不會被當作第二個起始來源。沒有補造原本缺少的括號，也沒有改寫已有的獨立起始網址。

有明確引號／角括號等邊界時，保留網址內的字面句尾標點；沒有邊界且沒有非空查詢的裸網址，仍沿用既有句尾標點處理。非空查詢參數則保留原字串，包括重複鍵、逗號、分號及問號，不猜測哪部分是參數值或句末標點。這類歧義可用明確的網址邊界或獨立 URL 參數排除。

規劃器與來源路由器也會容納無法解析的 authority，交由原本的無來源／無答案流程處理，不再因不完整 IPv6 網址直接拋錯。既有 Fetcher 的網址、帳密、私有位址與 DNS 檢查保持不變。

## 驗證與漏點修正

[最終固定 49 個規劃及本機 HTTP 檢查](../benchmarks/question-urls-20261023-v3.json)由 **19/49 到 49/49**，30 個改善、0 個退步，另有兩個掃描器順序檢查通過。11 個實際來源流程中，7 個原本因網址字串錯誤失敗的流程恢復，4 個原有成功保留。伺服器只接受完全符合預期的 request target，因此不是任何路徑都會回傳測試文件。

HTTP 檢查包含括號、巢狀括號、Markdown、原始編碼大小寫、重複鍵及簽章參數，並檢查實際回傳的來源 URL。模型停用時的固定文件標題只用來驗證讀取及輸出路徑，不能當作 Qwen 答題成績。

[真正 CLI／worker 的四個檢查](../benchmarks/question-urls-20261023-cli-v2.json)全部通過：括號網址、查詢參數、預設私有位址限制及格式錯誤的網址。結果檔與 trace 的 SHA256 均核對，模型呼叫數為零。

[第一輪 CLI](../benchmarks/question-urls-20261023-cli.json)原本只有 3/4 通過，發現規劃器雖已容納錯誤網址，來源路由仍會回傳 engine_error。先前的引擎檢查只要求空答案，因此漏掉此錯誤。現在路由已修正，檢查也要求不得以 engine_error 結束；早期報告保留，最終以 v3／CLI-v2 為準。

## 影響範圍

244 題已曝光資料的靜態規劃完全相同。它們全部具有獨立的起始 URL，沒有在問題文字中放網址，因此這項檢查不能證明新掃描器在既有競賽題目中增加答對數。

原始 `simpleqa-4145` 的起始網址早在上游資料中就已截斷；此次沒有修改該網址、標準答案或來源清單，也不把它視為已修復。最新整體答題分數保持原報告。

[最終驗證清單](../benchmarks/question-urls-20261023-verification.json)記錄命令、輸出與程式 SHA256。既有 CPU 回歸保持：服務／來源 16/16、代表性解析 15/15、搜尋發現 7/7、短查詢 9/9、組合證據 27/27。

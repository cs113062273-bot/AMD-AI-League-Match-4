## 新取得的資源證據

初始外部 100 題中，Windows GPUProcessMemory 計數器觀察到模型程序：專用記憶體 11,632,271,360 bytes、共享記憶體 2,285,895,680 bytes，亦即共享約 2.13 GiB。同時模型完成呼叫數曾長時間不變；後續外部 20 題亦觀察到約 2.01 GiB 共享記憶體。

這支持顯存壓力與服務排程參與長延遲的假說，**不是每一次 503 都由顯存造成的證明**。共享記憶體與 Torch allocated/peak 不是同一種計數；也不能推論 4B 權重本身必須使用 14GB。後續應同時量 allocated、reserved、driver/OS usage、prefill、decode、取消與 busy 時間。

原本「GPU 沒有明確證據」的檢討需要更新：現在有資源壓力的實測證據。但把型別標記當答案、錯誤 API 實體、來源不足及關係誤判，不會因增加顯存自動消失。

## 仍然存在的程式與評分問題

1. **API 實體誤辨**：WebScout n02 問不存在的 `zzqx-nonexistent-pkg-4821`，實際卻查 `/pypi/PyPI/json`，回 `2.1` 並標 direct_source。這是錯把 registry 名稱當 package 名稱，沒有經過模型，不能歸咎 Qwen。
2. **語意與多來源限制**：SourceTrail 的 HTML 全部由本機提供，主題組無 selector 503，仍只有答案 8/16、共同來源條件 7/16。跨版本比較、同版本矛盾、條件路線、有效日期政策均有失敗；16 號題 `$18` 答對，但只回一個來源，少了類別映射的另一來源。
3. **格式不能混成理解失敗**：Kaminari 原始字串 6/13，作者 scorer 11/13；單位與貨幣符號造成五題差異。剩餘 Titanic 日期也是等價格式而未通過作者規則；Rowling 題是真正空白。兩種原始計分都保留，不另外宣稱語意調整後的官方分數。
4. **外部 gold 可能過時**：WebScout v06 的既定答案是 Ollama 0.40.6，而實際 GitHub API 抽到 0.40.7；保留失分並標為需查版本時效，沒有改 gold。日期與電話格式也有可辨認失分。
5. **熟悉題的全過沒有代表性**：本次既有離線題是 329/330，與對手/廣域題落差仍大。保留集唯一退步為 release-size-3：模型選到整個標題 `Vega-1027 5.3.8`，因不符合 version 型別而回空白；紀錄內其實已有 `5.3.8` 候選。這暴露語意抽取、型別值與格式輸出的耦合，不是根本找不到版本。不能為修此例而無條件放行其他候選，必須保留實體與欄位證據。

SourceTrail 相容評分保留題目、別名、頁面與要求來源集合，但不重現其原生 status/quote schema、獨立 validator probes，且 Aperture 使用預設 10-page cap，作者原生為 6-page cap。不能把相容分數直接稱為其原生 benchmark 成績或正式排名。WebScout 作者自報 CPU 規則 39/40，我們在同公開問題及答案 normalization 下為 21/40，但仍有日期、硬體與網路差異。

## 容量與收尾

開測時 C 槽約 110.3 GiB 可用，過程一度約 94.1 GiB。本次結果與紀錄當時約 3.4 MiB，沒有新的模型、VM disk 或映像副本。Windows `pagefile.sys` 當時配置 26,981 MiB、目前使用 1,595 MiB、歷史峰值 8,854 MiB；系統 committed bytes 約 58.4GB，接近約 62.5GB commit limit。分頁檔自動擴張是容量變化的可能來源，但沒有開測前的同項計數，不能把全部差額確定歸因於它。

沒有刪除或修改系統分頁檔。全批結束後只關閉經 PID、command line 與本次啟動紀錄確認的模型程序；8765 已不監聽，GPU 使用量回到 519 MiB。C 槽恢復到 **109.8 GiB 可用**，接近開測的 110.3 GiB；分頁檔配置降為 15,377 MiB，系統 committed bytes 約 40.2GB。這顯示容量占用大部分會隨資源釋放恢復，不是測試產生了 16GB 的結果檔；仍不把每一個位元組差額都歸因於同一原因。
